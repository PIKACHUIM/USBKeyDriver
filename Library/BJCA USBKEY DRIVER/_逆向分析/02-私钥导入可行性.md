# 能否把外部私钥（PFX）导入 USBKey？

> **结论：不能。** 但结论的性质与旧文档不同 —— 旧文档是**从一次格式错误倒推**出来的"不支持"，
> 本文是通过**参数级实测**确认的"此路不通，且原因是缺少必要通道"。
>
> 设备：林果 LG3073（`6588:1514`，SN `5303201812001784`）　最后更新：2026-09-21

---

## 0. 先纠正一条旧结论

`Roadmap/07-BJCA逆向分析与对接.md` §8.2 曾写：

> **BJCA 不支持「导入外部私钥（PFX）」** …… 这符合 USBKey 的安全设计（私钥在卡内生成、不可导出也不可导入）

**这个结论不准确**。它是由一次失败倒推的，而那次失败的真实原因在组件 trace 里写得很清楚：

```
CXTXApp::ImportPfxToDevice starting
  → CryptokenBucket::ImportPFX
     DeviceSN(5303201812001784) Container(Pikachu...)
     [error] PKCS12_parse error!            ← 卡在「解析」阶段
```

**它连 PFX 都没解析开，根本没走到"卡是否肯写"那一步。**失败原因是旧测试用
`X509Certificate2.Export(X509ContentType.Pfx, pwd)` 生成 PFX —— 在 .NET 5+ 上这默认产出
**PBES2（PBKDF2 + AES-256 + SHA256）**，而组件的 `PKCS12_parse` 是 OpenSSL 老 API，**不认 PBES2**。

## 1. 三条路径的实测结论

| 方案 | 路径 | 结论 |
|------|------|------|
| **A** | SKF 国标 `SKF_ImportRSAKeyPair` | ❌ **接口存在，但缺少获取「设备加密公钥」的通道** |
| **B** | 卡内生成密钥对 + CA 签发 + `ImportCertificate` | ✅ **唯一可用**（已走通） |
| **C** | BJCA 官方客户端 / `ImportPfxToDevice` | ❌ 内部实现存在并走到最后一步，但仍失败 |

## 2. 方案 A：SKF `SKF_ImportRSAKeyPair` 实测全过程

### 2.1 接口确认

```
tools/bjca_analyze.py argcounts  →  SKF_ImportRSAKeyPair  args=6  (ret $0x18)
```

**6 参数，与 GM/T 0016 国标完全一致**，故按国标声明即可。国标语义：

```c
ULONG SKF_ImportRSAKeyPair(
    HANDLE hContainer,
    ULONG  ulSymAlgId,        // 对称算法标识
    BYTE  *pbWrappedKey,      // 【用对称密钥加密后的 RSA 私钥】
    ULONG  ulWrappedKeyLen,
    BYTE  *pbEncryptedKey,    // 【用设备密钥加密公钥加密后的对称密钥】
    ULONG  ulEncryptedKeyLen);
```

### 2.2 第一步：空容器调用 → `0x0A000031 文件不存在`

```
SKF_CreateContainer(ZZIMPORTTEST)   → 成功
SKF_ImportRSAKeyPair 空负载：
  symAlgId=0x00000000  → 文件不存在（0x0A000031）
  symAlgId=0x00000101  → 文件不存在（0x0A000031）
  symAlgId=0x00000401  → 文件不存在（0x0A000031）
  symAlgId=0x00000801  → 文件不存在（0x0A000031）
```

**结论**：容器内必须**先有密钥对**才能导入，且与 `symAlgId` 取值无关。

### 2.3 第二步（分水岭）：容器内生成密钥对后 → `0x0A000019 RSA解密错误`

```
SKF_GenRSAKeyPair(1024)        → 成功
生成后 签名公钥 → 成功 len=268
生成后 加密公钥 → 文件不存在（0x0A000031）      ← 注意：加密密钥对仍不存在
生成后再调 ImportRSAKeyPair → RSA解密错误（0x0A000019）   ★ 错误码改变！
```

**这一步很关键**：错误码从"文件不存在"变成"RSA 解密错误"，说明**中间件确实开始执行 RSA 解密**，
参数方向与国标一致。同时说明：**容器的解密能力来自那份密钥对**（`GenRSAKeyPair` 生成的），
而 `SKF_ExportPublicKey(sign=false)` 找的是另一个东西（专门的"加密密钥对"文件）。

### 2.4 第三步：按国标构造真实参数 → 仍报 `0x0A000019`

参数构造（全部按国标语义）：

```
容器公钥   ← SKF_ExportPublicKey(sign=true)，268 字节厂商 blob，已还原为 1024 位 RSA 公钥
待导入私钥 ← RSA-1024 的 PKCS#1 DER，607 字节
pbWrappedKey   = 对称密钥(AES-128-ECB/PKCS7) 加密私钥   → 608 字节
pbEncryptedKey = 容器公钥 加密 对称密钥                  → 128 字节
```

**遍历了 16 组组合**（2 种字节序 × 2 种 padding × 4 种对称算法）：

```
── 公钥字节序：大端 ──                    ── 公钥字节序：小端 ──
PKCS#1v1.5  AES128_ECB → 0x0A000019      PKCS#1v1.5  AES128_ECB → 0x0A000019
PKCS#1v1.5  AES128_CBC → 0x0A000019      PKCS#1v1.5  AES128_CBC → 0x0A000019
PKCS#1v1.5  SM4_ECB    → 0x0A000019      PKCS#1v1.5  SM4_ECB    → 0x0A000019
PKCS#1v1.5  SM4_CBC    → 0x0A000019      PKCS#1v1.5  SM4_CBC    → 0x0A000019
OAEP-SHA1   AES128_ECB → 0x0A000019      OAEP-SHA1   AES128_ECB → 0x0A000019
OAEP-SHA1   AES128_CBC → 0x0A000019      OAEP-SHA1   AES128_CBC → 0x0A000019
OAEP-SHA1   SM4_ECB    → 0x0A000019      OAEP-SHA1   SM4_ECB    → 0x0A000019
OAEP-SHA1   SM4_CBC    → 0x0A000019      OAEP-SHA1   SM4_CBC    → 0x0A000019
```

### 2.5 结论与推理

**错误码 16 组完全一致、一字不变** —— 这本身就是最强线索：

- 如果它解的是我传入的 `pbEncryptedKey`，那我**用的就是容器自己的公钥**加密，容器私钥理应能解开，
  **不该报解密错误**；
- 既然结果与 `pbEncryptedKey` 的内容**完全无关**，说明**它用的是另一把私钥**；
- 那把私钥只能是**设备级的「密钥加密私钥」**。

**而导出对应「设备加密公钥」的接口，在中间件的 100 个导出里一个都没有**：

```
EPS_Decrypt / EPS_Encrypt / EPS_ImportSymmKey / EPS_Mac / EPS_ReadESealData / EPS_WriteESealData
SKF_DevAuth / SKF_ChangeDevAuthKey          ← 设备认证（厂商密钥域，挑战应答）
SKF_RSAExportSessionKey / SKF_ECCExportSessionKey   ← 方向相反：用外部公钥加密会话密钥并导出
SKF_ImportSessionKey / SKF_SetSymmKey
SKF_ExportPublicKey                          ← 容器级，非设备级
```

**没有 `GetDevicePublicKey` 一类接口。** 而 `SKF_DevAuth` 是**挑战应答**，
需要**厂商持有、出厂注入的认证密钥** —— 拿不到。

### 2.6 设备能力位图（实测）


## 3. 方案 A 之外的发现：BJCA 内部另有一条实现

虽然对外报 `0x0B000028`，但组件内部**确实实现了导入**，函数名直指其能力：

```
CXTXApp::ImportPfxToDevice                     (XTXApp.cpp:2952)
  → CryptokenBucket::ImportPFX                 (cryptobucket.cpp:5395)
     → SKFApplicationWrap::CreateContainer     ← 容器建成功
     → CryptokenBucket::ImportPlainKeyCert     (cryptobucket.cpp:5262)  ★ 导入明文密钥+证书
        → x509Parser::GetPublicKey             ← 解析证书 OK
        → Soft_RSASignHash + Soft_RSAVerify    ← 用私钥签名再用证书公钥验签（证明密钥匹配）OK
        → SKFApplicationWrap::VerifyPIN        ← 组件自动做了 PIN 认证，成功
        → [status=0x00000002] at cryptobucket.cpp(5369)   ★ 失败点
```

**（报错为 `GetLastError=18`、`GetLastErrMsg=导入证书失败`）**

### 3.1 PFX 编码与密钥算法的实测影响

| PFX 类型 | 错误码 | 错误信息 | 容器 |
|----------|--------|----------|------|
| **RSA-1024 / RSA-2048（PBES1）** | 18 | **导入证书失败** | **建了**（走最远） |
| EC P-256（PBES1） | 42 | 签名失败 | 没建 |
| SM2（PBES1） | 61 | 解析PKCS12失败 | 没建 |
| RSA（**PBES2/AES 现代编码**） | — | **`PKCS12_parse error`** | 没建 |

**三个入场条件（均已实测）**：

1. **PFX 必须是老式编码**（PBES1：3DES/RC2 + SHA1）—— 现代 PBES2 在 `PKCS12_parse` 阶段就被拒；
2. **必须含 RSA 私钥** —— 组件用 `d2i_RSAPrivateKey` 解析，EC/SM2 直接失败
   （实测日志：`cert public key len:65` = EC/SM2 公钥格式 → `call d2i_RSAPrivateKey error!`）；
3. **需 PIN 认证** —— 组件会**自动**调用 `SKF_VerifyPIN`，实测认证成功。

即使三条都满足，**最后仍失败**（`status=0x00000002`），且失败点位于
**建容器成功之后、真正写入密钥之前** —— 与 SKF 那条"缺少设备密钥"高度一致，很可能同一根因。

### 3.2 复现方法

```bash
# 生成老式编码 PFX（PBES1: 3DES + SHA1）
openssl req -x509 -newkey rsa:2048 -keyout k.pem -out c.pem -days 365 -nodes -subj "/CN=BJCAPFXTEST/O=USBKeyDriver"
openssl pkcs12 -export -certpbe PBE-SHA1-3DES -keypbe PBE-SHA1-3DES -macalg sha1 \
        -inkey k.pem -in c.pem -out legacy.pfx -passout pass:1234

# 实测导入
BjcaProbe pfximport <路径>\legacy.pfx 1234 --cleanup
```

样本见 [`samples/pfx/`](./samples/pfx/)。

## 4. 最终结论

**这张卡上的私钥只能卡内生成，无法从外部导入。**

与旧文档的区别在于，这个结论现在有完整实证链条：

| 环节 | 状态 |
|------|------|
| SKF 国标接口是否存在 | ✅ 存在（6 参数与国标一致） |
| 参数构造是否正确 | ✅ 已按国标构造并遍历 16 组组合 |
| 前置条件是否满足 | ✅ 容器已建、密钥对已生成、认证已完成 |
| 失败原因 | ❌ **缺少获取「设备加密公钥」的通道**，该通道被关在 `SKF_DevAuth` 厂商认证域内 |
| BJCA 侧是否有旁路 | ❌ 内部实现存在且走到最后一步，同样失败 |

**仍然存在的两种可能性**（若日后需要继续推进）：

1. **向林果索取「设备包装密钥 / 导入授权」** —— 厂商工具链可能具备该能力，只是不经公开 SKF 接口暴露；
2. **解开 BJCA 的 `status=0x00000002`** —— 它已走到密钥包装前一步，若该错误码能被解释，也许能绕开 SKF 侧限制。

## 5. 推荐做法（当前唯一可行路径）

```
① SKF_CreateContainer          建容器
② SKF_GenRSAKeyPair            卡内生成密钥对（RSA 约 30~90 秒）
③ SKF_ExportPublicKey          导出公钥
④ 组织 PKCS#10 / CSR 交 CA 签发
⑤ SKF_ImportCertificate        证书导回卡内
```

Manager 中对应「证书登记」向导（`EnrollForm`）。

> **注意**：SKF 的建容器同样要求先认证 —— 未认证时 `SKF_CreateContainer` 直接返回
> `0x0A00002D 用户没有登录`。`EnrollForm` 已在建容器前加入认证步骤（用户 PIN）。
