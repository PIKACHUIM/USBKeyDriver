# 容器管理：删除权限、缓存机制与双向同步

> 记录三个曾导致现场故障（"删除失败""删除后仍显示"）的机制性原因，附零写入实验证据。
>
> 设备：林果 LG3073（`6588:1514`，SN `5303201812001784`）　最后更新：2026-09-21

---

## 1. 删除容器是否必须先认证？

### 1.1 旧依据其实是推断

`Roadmap/08-SKF(GM-T0016)通用对接.md` §5 曾写「认证（删除容器需要管理员权限）」——
但核对后发现这是**推断**：该文档 §4 表格里"删除容器 ✅"发生时，会话中
**用户 PIN（步骤 2）与管理口令（步骤 10）都已认证过**，无法区分究竟哪种 PIN 是必要条件。

### 1.2 零写入对照实验

`CertListProbe skf --probe-delete-perm`：用一个**卡上不存在**的容器名调用
`SKF_DeleteContainer`，比较不同认证状态下的返回码。
因容器名不存在，实验中**不会创建、删除或修改卡上任何数据**。

| # | 会话状态 | 返回 |
|--:|----------|------|
| ① | 未认证 | **`0x0A00002D` 用户没有登录** |
| ② | 已认证管理口令 `type=0` | `0x0A00002E` 应用不存在 |

### 1.3 结论

1. **删除容器前必须完成认证** —— 中间件在**第一步**就检查认证状态，连"容器是否存在"都还没查
   （对比 ②：认证后才进入目标查找）。因此删除前的认证**不是可选项，也无法绕过**。
2. **`0x0A00002E` 的真实含义是「目标容器不存在」**，而非字面的"应用不存在"——
   证据：用任意一个不存在的容器名调用，返回的都是这个码（见上表 ②，以及 BJCA 侧的同类现象）。
3. **尚未证实**：`0x0A00002D` 的措辞是"用户**没有登录**"（泛指认证），
   因此**用户 PIN（`type=1`）认证后是否同样允许删除，仍未验证**
   （验证需当前有效的用户 PIN；本机卡的用户 PIN 已非出厂值 `123456`）。

> **权限模型的原理**：GM/T 0016 在应用内定义两套凭据 ——
> **管理口令（SO PIN, type=0）管「结构」**（建/删容器、管文件、重设用户 PIN）；
> **用户 PIN（type=1）管「使用」**（登录、签名、解密）。删除容器属结构操作，故归管理口令管辖。

> ⚠️ **每次 PIN 认证失败都会真实消耗一次重试次数（上限 10），不要猜测口令做试探。**

## 2. BJCA 用户列表的缓存机制（"僵尸数据"成因）

### 2.1 现象

用 SKF 删除卡内容器后，BJCA 侧**仍然列出该证书**；再次删除则失败。

### 2.2 两个数据源的真实行为

| 接口 | 实际是什么 | 行为 |
|------|-----------|------|
| `SOF_GetAllContainerName`（dispid 79） | **卡内真实容器** | SKF 删掉后**立即变空** |
| `SOF_GetUserList`（dispid 5） | **组件进程内的缓存** | **完全不随卡内容器变化** |

现场日志（Manager）：

```
21:40:42  SOF_GetUserList="Test User||UserKey/5303201812001784&&&"  GetAllContainerName="UserKey&&&"

21:40:49  SOF_GetUserList="Test User||UserKey/5303201812001784&&&"  GetAllContainerName=""     ← 容器被删后
```

**`SOF_GetUserList` 从头到尾一个字都没变。**

### 2.3 它是"进程内缓存"而非持久化数据

同一组件、同一张卡、**不同进程**返回不同：

| 时间 | 进程 | `SOF_GetUserList` 返回 |
|------|------|------------------------|
| 21:44:12 | 旧 Manager（pid 35816） | `Test User\|\|UserKey/5303201812001784&&&` |
| 21:48:44 | BjcaProbe（新进程） | `()` |
| 21:49:45 | 新 Manager（pid 15012） | `()` |

实现路径（组件 trace）：

```
CXTXApp::SOF_GetUserList                     (XTXApp.cpp:157)
  → CryptokenBucket::GetUserListString       (cryptobucket.cpp:250)
```

**结论**：该列表是 **`CryptokenBucket` 的进程内会话缓存**，
**既不落卡、也不落盘** —— **重启管理器即彻底消失**。因此清理它无需触碰卡上任何文件。

### 2.4 残留条目确实是"坏数据"

trace 显示组件把残留的 `Test User` 当成**设备序列号**去打开：

```
CXTXApp::SOF_ExportUserCert - szCertID:Test User
CryptokenBucket::ExportUserCert CertID(Test User)
CryptokenManager::OpenDevice DeviceSN(Test User)
  [error] Can not OpenDevice(Test User)!        ← 必然失败
```

### 2.5 已实施的修复

**`BjcaProvider.ListContainers` 的悬空条目过滤**，原有一个前置条件
`if (realContainers.Count > 0)` —— 它带来一个更糟的后果：**卡内容器被清空后过滤整体失效**，
残留条目重新出现在列表里。**已去掉该前置条件**，改为始终过滤，并保留两道安全网：

1. 能成功导出证书的条目会被标为 `Certificate`，**永不进入过滤**（最关键的一道）；
2. `realContainers` 来自 `SOF_GetAllContainerName`，实测是实时读卡的真值，可作"卡上是否真有该容器"的判据。

被过滤的条目不静默丢弃，写日志便于追查。

## 3. 两侧名称空间不同（删除失败的另一个坑）

### 3.1 两套命名格式

| 来源 | 格式 | 示例 |
|------|------|------|
| BJCA `SOF_GetUserList` | **容器名 / 设备序列号** | `UserKey/5303201812001784` |
| SKF `SKF_EnumContainer` | **纯容器名** | `UserKey` |

**不归一化就永远匹配不上。**

### 3.2 曾导致的故障

在 BJCA 条目上点删除 → 自动回退到 SKF → **把带 `/序列号` 的名字直接传给 `SKF_DeleteContainer`**
→ 因找不到容器而返回**含义含糊的 `0x0A00002E`**。

### 3.3 已实施的修复

`MainForm.DoDeleteCert`：**回退前先按名字在 SKF 侧查找**（用归一化后的名字比对）——

- **找到** → 用 SKF 侧的真实条目执行删除（名字与"内容类型"都以卡上为准）；
- **找不到** → 抛出明确原因，而不是甩一个 `0x0A00002E`：

> 卡上（SKF 视角）不存在容器「Test User」。
> 原因：该条目只存在于「北京CA」组件自己的记录里（SOF_GetUserList），卡内并没有对应的容器实体。
> 这两者是相互独立的数据源 —— 用 SKF 删除卡内容器，不会同步清理 BJCA 的那份记录。
> 当前卡上真实存在的容器：（无）

## 4. 双向同步删除（已实现）

需求：**从任一侧删除，两侧的列表都要清干净**。

| 从哪一侧删除 | 行为 |
|--------------|------|
| **BJCA 条目** | 回退到 SKF 删卡内容器（权威动作）；BJCA 侧再同步一次 |
| **SKF 条目** | 删卡内容器；**再调一次 BJCA 的删除**，促使组件刷新自身缓存 |

实现：`MainForm.DoDeleteCert` → `SyncBjcaDelete(sn, containerName)`

**BJCA 那次同步调用失败是预期结果**（容器已不在 → 组件返回 `0x0B000028`），
故**静默忽略并写日志**，不影响已成功完成的删除。

## 5. 另一处待修问题：BJCA 看不到卡上的证书

### 5.1 现象

在 BJCA 侧完成"证书登记"后，SKF 能看到证书，BJCA 却只显示「容器（无证书）」。

### 5.2 根因

`SOF_GetUserList` **恒为空**（见 §2），而它是定位证书 ID 的唯一正规入口 →
拿不到 CertID → 无法调 `SOF_ExportUserCert` → 只能退化成容器兜底分支。

### 5.3 修复：按 CertID 约定自行构造

trace 日志暴露了 CertID 的确定构成：

```
CXTXApp::SOF_ExportUserCert - szCertID:UserKey/5303201812001784
                              ↑ 容器名 + '/' + 设备序列号
```

既然格式确定，就不必依赖那个不可靠的列表接口：对 `SOF_GetAllContainerName` 里的每个容器，
**自行拼出 `容器名/序列号` 去取证书**。

实现：`BjcaProvider.TryExportCertificateByConvention`。

**实测结果**（修复后）：

```
类型    容器名                      算法    证书CN       有效期                     已注册
证书    UserKey/5303201812001784    RSA    Test User    2026-09-21 ~ 2027-09-21   是
```

**与 SKF 侧显示完全一致。**
