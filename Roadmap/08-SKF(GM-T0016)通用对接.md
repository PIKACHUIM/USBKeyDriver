# SKF（GM/T 0016）通用 USBKey 对接

> **目标**：绕开厂商客户端私有缓存，直接 P/Invoke 厂商 **SKF 中间件**，
> 拿到 **枚举 / 登录 / 改密 / 解锁 / 容器读写 / 证书导入导出 / 重置** 的全套能力。
>
> **状态**：✅ 已完成并**全链路实机验证**（设备：林果 LG3073，`6588:1514`，SN `5303201812001784`）。
>
> **日期**：2026-09-21 · 工具：`Manager/tools/SkfProbe` · `tools/bjca_analyze.py`

---

## 1. 为什么需要这条路

BJCA 的 `XTXAppCOM` 组件能重置设备，但其**登录 / 改密 / 导出证书**依赖 `SOF_GetUserList` 取 `CertID`，
而该列表在实测中**恒为空**（详见 [`07-BJCA逆向分析与对接.md`](./07-BJCA逆向分析与对接.md) §8.3），链路无法自举。

而 `Driver\driver.ini` 显示本设备 `type = SKF`、`dll = lgu3073_p1514_gm.dll`，
即**厂商提供的是标准 SKF 中间件**。SKF 是国标（GM/T 0016-2012），接口稳定、语义完整，
且**不依赖任何客户端缓存**——这是最彻底的对接方式。

## 2. 对接目标

| 项 | 值 |
|---|---|
| 中间件（32 位） | `Library\BJCA USBKEY DRIVER\BJCAClient\CertAppEnvV3.7.418.0052\Driver\x86\lgu3073_p1514_gm.dll` |
| 中间件（64 位） | 同目录 `x64\lgu3073_p1514_gm_x64.dll` |
| 导出数量 | **100 个**，含完整 `SKF_*` 家族 + `EPS_*`/`SKFEX_*` 厂商扩展 |
| 调用约定 | `__stdcall`，返回 `ULONG`（`SAR_OK=0`，错误码 `0x0A0000xx`） |

**参数个数核对**（`tools/bjca_analyze.py argcounts`，用 `ret imm16` 推算）：
所用作 40 余个接口与 **GM/T 0016 国标签名逐条完全一致**，例如

| 函数 | 实测 args | 国标 |
|---|---:|---|
| `SKF_EnumDev` | 3 | `(BOOL bPresent, LPSTR pszNameList, ULONG* pulSize)` |
| `SKF_ConnectDev` | 2 | `(LPSTR szName, HANDLE* phDev)` |
| `SKF_GetDevInfo` | 2 | `(HANDLE hDev, DEVINFO* pDevInfo)` |
| `SKF_VerifyPIN` | 4 | `(HANDLE hApp, ULONG ulPINType, LPSTR szPIN, ULONG* pulRetryCount)` |
| `SKF_ChangePIN` | 5 | `(HANDLE hApp, ULONG ulPINType, LPSTR szOldPin, LPSTR szNewPin, ULONG* pulRetryCount)` |
| `SKF_UnblockPIN` | 4 | `(HANDLE hApp, LPSTR szAdminPIN, LPSTR szNewUserPIN, ULONG* pulRetryCount)` |
| `SKF_CreateApplication` | 8 | `(hDev, app, adminPin, adminRetry, userPin, userRetry, fileRights, HANDLE* phApp)` |
| `SKF_ImportCertificate` / `SKF_ExportCertificate` | 4 / 4 | `(hContainer, BOOL bSignFlag, BYTE* pbCert, ULONG[ *] len)` |

> 因此**直接按国标签名 P/Invoke 即可**，无需逐函数逆向。少数私有扩展（`SKF_GetContainerInfo` 7 参数、
> `SKF_ReadFile` 6 参数、`SKF_WriteFile` 5 参数）与国标不同，暂未使用。

## 3. 关键实测结论

### 3.1 设备与应用

| 项 | 实测值 |
|---|---|
| `SKF_EnumDev` 返回 | 设备名 = **序列号**（`5303201812001784`），设备数 1 |
| `SKF_GetDevState` | `1`（已插入；`2` = 已锁定） |
| `SKF_EnumApplication` | `BJCA-Application`（唯一） |
| `SKF_OpenApplication("BJCA-Application")` | 成功 |

### 3.2 **PIN 类型：0 = 管理员，1 = 用户**（关键！）

实测（`SKF_VerifyPIN`）：

| 调用 | 结果 |
|---|---|
| `(type=0, "111111")` | ✅ **成功** |
| `(type=0, "123456")` | ❌ PIN 无效 |
| `(type=1, "111111")` | ❌ PIN 无效 |
| `(type=1, "123456")` | ✅ **成功** |

而 `SKF_GetPINInfo(type=2/3/4/5)` 一律返回 `SAR_INVALIDPARAMERR(0x0A000006)`。

> ⚠️ 注意：这与「1=admin / 2=user」的常见写法相反，**必须以实测为准**。
> 另外测试会**消耗重试次数**（每次失败 -1，当前上限 10）。

> **时效性警告（2026-09-21 复测补充）**：上表的出厂口令（管理口令/用户 PIN 均 `111111`、`123456`）
> **只适用于尚未被修改过的卡**。本机这张 LG3073 复测时 `SKF_VerifyPIN(1, "123456")` 已返回
> `0x0A000026 PIN 无效`（用户 PIN 已被改过），说明**该记录已过期**。
> 代码/文档中出现的默认口令只能作为「首次使用且未改过口令」的兜底，**不得当作通用事实**。

### 3.3 `DEVINFO` 是厂商变体（偏移 ≠ 国标）

`SKF_GetDevInfo` 的原始转储显示其结构体与国标不同：

```
000  01 03 "Linguo Tech" ...          ← 0x00 USHORT Version（2 字节！国标为 ULONG）
002  Label[64]        = "Linguo Tech"
042  Manufacturer[64] = "Linguo Tech"
082  Issuer[32]       = "BJCA-UserKey"
0A2  SerialNumber[32] = "5303201812001784"
0C2  起为数值区（HW/FW/算法能力…）
```

国标为 `ULONG Version; char Label[32]; char Manufacturer[64]; char Issuer[64]; char SerialNumber[32];`，
本中间件是它的变体。**且结构体 > 256 字节：用 256 字节缓冲区会被越界写导致进程崩溃**，
实现里已改用 4096 字节。

### 3.4 `SKF_DeleteApplication` 不可用（需厂商设备认证）

| 组合 | 结果 |
|---|---|
| 打开应用 → 管理口令认证 → 关闭应用 → 删除 | `0x0A00002D 用户没有登录` |
| 打开应用 → 管理口令认证 → 直接删除 | 同上 |
| 打开应用 → 用户 PIN 认证 → 直接删除 | 同上 |
| `SKF_VerifyPIN(设备句柄, …)` | ⚠️ **进程崩溃**（设备句柄不能当应用句柄用） |

结论：删除/重建应用依赖 **`SKF_DevAuth` 设备认证（厂商密钥 + 挑战应答）**，非 PIN 通道，
属厂商私有能力，**未对接**。因此重置改用下面的等价组合。

### 3.5 `SKF_DeleteContainer` 的权限要求（零写入对照实验）

> **背景修正**：§5 流程图里原先标注的「删除容器需要管理员权限」当时是**推断**——
> §4 表格第 11 项删除容器成功时，会话中用户 PIN（步骤 2）与管理口令（步骤 10）**都已认证**，
> 无法区分究竟哪种 PIN 才是必要条件。为消除这个不确定性，补做了下面的实验。

实验方式（`CertListProbe skf --probe-delete-perm`，**零写入**）：
用一个**卡上不存在**的容器名调用 `SKF_DeleteContainer`，比较不同认证状态下的返回码。
因容器名不存在，实验中不会创建、删除或修改卡上任何数据。

| # | 会话状态 | 返回 |
|--:|---|---|
| ① | 未认证 | **`0x0A00002D` 用户没有登录** |
| ② | 已认证管理口令 `type=0` | `0x0A00002E` 应用不存在 |

**结论**：

1. **删除容器前必须完成认证**——中间件在第一步就检查认证状态，连「容器是否存在」都还没查
   （对比 ② 认证后才进入目标查找）。因此删除前的 PIN 认证**不是可选项，也无法绕过**。
2. `0x0A00002E「应用不存在」` 是在「已认证 + 目标容器名不存在」时出现的文案，
   语义上更像是厂商对「找不到该容器」的不精确表述（未用真实容器名复验，避免误删数据）。
3. **尚未证实**：`0x0A00002D` 的措辞是「用户没有登录」（泛指认证），
   因此**用户 PIN（type=1）认证后是否同样允许删除，仍未验证**——
   验证需要当前有效的用户 PIN（本机卡的用户 PIN 已非出厂值 `123456`，见 §3.2 警告）。

> **重申**：每次 PIN 认证失败都会真实消耗一次重试次数（上限 10），**不要猜测 PIN 做试探**。

## 4. 全链路实机验证结果

`SkfProbe flow 123456 111111 [--reset]`（每一步都打印真实返回码）：

| # | 功能 | 对应 SKF 接口 | 结果 |
|--:|------|---------------|------|
| 1 | 枚举设备 / 详情 | `SKF_EnumDev` / `ConnectDev` / `GetDevInfo` | ✅ |
| 2 | **登录**（用户 PIN） | `SKF_VerifyPIN(type=1)` | ✅ |
| 3 | 建容器 | `SKF_CreateContainer` | ✅ |
| 4 | 卡内生成密钥对 | `SKF_GenRSAKeyPair(1024)` | ✅ |
| 5 | 导出公钥 | `SKF_ExportPublicKey` | ✅ 268B blob |
| 6 | **导入证书** | `SKF_ImportCertificate` | ✅ 611B 证书导入成功 |
| 7 | 回读证书 | `SKF_ExportCertificate` | ✅ 与导入**完全一致** |
| 8 | 列容器（含证书信息） | `SKF_EnumContainer` / `OpenContainer` / `GetContainerType` | ✅ |
| 9 | **改密** | `SKF_ChangePIN(type=1)` | ✅ 改后新 PIN 登录成功，并成功改回 |
| 10 | **解锁**（重置用户 PIN） | `SKF_UnblockPIN(管理口令, 新用户PIN)` | ✅ 解锁后新 PIN 登录成功，并成功还原 |
| 11 | 删除容器 | `SKF_DeleteContainer` | ✅ |
| 12 | **重置** | 见 §5 | ✅ |

`SKF_ExportPublicKey` 的 blob 布局（实测，268 字节）：

```
[0..3]   4B 头（保留/类型）
[4..7]   ULONG ulBitsLen（小端，1024）
[8..263] Modulus[256]（小密钥右对齐：1024bit 时有效数据在 [136..263]）
[264..267] Exponent[4]（大端，`00 01 00 01` = 65537）
```

> 依据此布局可把容器公钥还原成标准 RSA 公钥，交给 CA 签发后 `SKF_ImportCertificate` 导回，
> 即完成**不依赖厂商客户端**的「证书申请 → 导入」闭环（探针已实测通过）。

## 5. 重置（清空内容 + 重设两套口令）

由于 `SKF_DeleteApplication` 不可用，改为**全部由已实测成功的标准接口组合**：

```
1) SKF_VerifyPIN(type=0, 当前管理口令)          认证（删除容器前**必须**认证，见 §3.5 实测）
2) SKF_EnumContainer + SKF_DeleteContainer      逐个删除全部容器（密钥 + 证书）
3) SKF_EnumFiles + SKF_DeleteFile               删除应用内全部文件
4) SKF_ChangePIN(type=0, 当前管理口令, 新管理口令)  改管理口令（新旧不同才执行）
5) SKF_UnblockPIN(新管理口令, 新用户 PIN)        强制重设用户 PIN（★不需要旧用户 PIN）
6) 复验：用新管理口令与新用户 PIN 分别 VerifyPIN
```

**实机执行报告**：

```
1) 认证管理口令 → 成功
2) 重置前容器数 0
3) 应用内文件数 0（枚举 成功）
4) 管理口令不变，跳过修改
5) SKF_UnblockPIN(新管理口令, 新用户PIN) → 成功
6) 复验新管理口令 → 成功
   复验新用户 PIN → 成功
   重置后容器数: 0
```

### 管理器中的入参映射（`IKeyProvider.ResetDevice`）

| 接口参数 | SKF 语义 |
|---|---|
| `currentPin` | **当前管理口令**（认证用；出厂值 `111111`） |
| `adminKey` | **新管理口令**（留空 = 沿用当前） |
| `newPin` | **新用户 PIN** |
| `puk` | 不使用（SKF 无独立 PUK，解锁由管理口令承担） |
| `ResetRequiresCurrentPin` | `true`（UI 会先要求输入当前管理口令） |

## 7. 配置与部署

```jsonc
// config.json
"platform": [ "lnca", "hengbao", "epass3003", "linguo", "gm3000", "bjca", "skf" ],
"keyslist": {
  "skf": [
    {
      "name": "林果 LG3073（BJCA 定制，SKF/GM-T 0016 中间件）",
      "vid": "6588",
      "pid": "1514",
      "dll": "lgu3073_p1514_gm.dll"      // 会在 Library 下递归查找；x64 宿主自动换 _x64 版本
    }
  ]
}
```

* VID/PID 仅用于展示与过滤；SKF 本身不提供 VID/PID（配置里给了非零值才回填）。
* 中间件仍依赖已安装的读卡器/驱动（BJCA 客户端提供的 `USB Token 32 Holder`）。
* 若要支持其他厂商的 SKF 中间件，只需在 `keyslist.skf` 增加一项并填 `dll` 文件名即可 —— **provider 是通用的**。

## 8. 与 BJCA（XTXAppCOM）路线的分工

| 能力 | BJCA/XTXAppCOM（platform `bjca`） | SKF（platform `skf`） |
|------|-----------------------------------|------------------------|
| 重置（清空 + 重设两套口令） | ✅ `InitDeviceEx`（不需旧口令） | ✅ 容器/文件删除 + `ChangePIN`/`UnblockPIN`（需当前管理口令） |
| 登录 / 改密 / 解锁 | ⚠️ 依赖 `CertID`，实测取不到 | ✅ 完整可用 |
| 容器 / 证书导入导出 | ⚠️ 同上 | ✅ 完整可用 |
| 覆盖范围 | BJCA 客户端支持的全部型号（自动分派） | 仅配置了 SKF 中间件的型号 |

> 建议：**BJCA 卡优先用 `skf` 平台**；若某型号没有 SKF 中间件，再用 `bjca` 平台做重置。

## 9. 遗留问题

1. **设备认证（`SKF_DevAuth`）未对接**：因此无法 `SKF_DeleteApplication`/`CreateApplication`
   （即无法真正「恢复出厂」，只能清空容器与文件 + 重设口令）。需要拿到厂商设备认证密钥与算法。
2. **`SKF_ReadFile` / `SKF_WriteFile` 参数个数与国标不同**（6/5 vs 5/4），未对接，
   故「卡内文件读写」暂未纳入 provider（`EnumFiles`/`DeleteFile` 已用于重置清理）。
3. **证书申请（PKCS#10）未封装**：探针里已验证「用导出公钥构造证书 → CA 签发 → 导入」可行，
   但完整的 CSR 生成（需用卡内私钥 `SKF_RSASignData` 签名，摘要算法待确认）尚未做成产品功能。
4. **私钥导入（PFX）不支持**：SKF 的私钥在卡内生成、不可导出也不可导入（安全设计）；
   `SKF_ImportRSAKeyPair` 需要「被保护的密钥对」格式（厂商工具产出），未对接。
